# Azure OpenStack Deployment Flow

End-to-end walk-through from a successful `terraform apply` to a running
OpenStack cluster you can log into via Horizon. **Designed to run once,
top-to-bottom, with no troubleshooting detours.**

> **Starting point**: you've just run `terraform apply plan.out` in
> `prod-setup/azure/terraform/` and it succeeded. All four VMs (bastion,
> controller, compute-1, compute-2) are up in Azure, and `kolla-config/multinode`
> has been re-rendered from `azure/terraform/multinode.tftpl` with the
> Terraform-managed IPs.

> **First-time / upgraded checkout**: the Terraform module now uses the
> `hashicorp/local` provider to render the Kolla inventory. If you cloned this
> repo before that change, run `terraform init -upgrade` once before `plan` so
> the local provider gets installed.

> **Why this flow looks paranoid in places**: macOS's SSH agent silently
> auto-loads keys from the login keychain, even after `ssh-add -D`. That breaks
> `ssh-copy-id` and plain agent-forwarded `ssh` because the forwarded agent ends
> up offering 6+ keys, tripping `MaxAuthTries=6` on the target. The flow below
> copies a single explicit key to the bastion and bypasses the agent entirely —
> guaranteed one auth attempt per host, no surprises.

Every command block starts with a `# === LAPTOP ===` or `# === BASTION ===`
marker so you always know where to run it.

## Step 0 — Capture Terraform outputs

```bash
# === LAPTOP ===
cd /Users/hanzo/code/openstack/prod-setup/azure/terraform

terraform output                              # full list
terraform output -raw bastion_public_ip       # save this
terraform output -raw kolla_inventory         # cross-check IPs match kolla-config/multinode
```

## Step 1 — Set up the laptop's SSH config

The generated snippet is wrapped in `# === BEGIN openstack-prod (Azure) ===`
… `# === END openstack-prod (Azure) ===` markers so re-applies are idempotent.

**First time** — append:

```bash
# === LAPTOP ===
terraform output -raw ssh_config >> ~/.ssh/config
```

**Re-apply after IPs/keys changed** — replace the existing block in place
(idempotent; safe to run repeatedly):

```bash
# === LAPTOP ===
NEW=$(terraform output -raw ssh_config)
awk -v new="$NEW" '
  /^# === BEGIN openstack-prod \(Azure\) ===$/ { print new; skip=1; next }
  /^# === END openstack-prod \(Azure\) ===$/   { skip=0; next }
  !skip
' ~/.ssh/config > ~/.ssh/config.tmp && mv ~/.ssh/config.tmp ~/.ssh/config
```

The generated snippet contains `IdentityFile`, `IdentitiesOnly yes`,
`ForwardAgent no`, and `ProxyJump bastion` per host. Result: the laptop
offers **only** your `openstack-prod` key on each hop, and (critically)
nothing leaks into the bastion via a forwarded agent — DEPLOY.md Step 5's
"too many auth failures" trap is avoided automatically.

**No `ssh-add` dance needed** — `IdentitiesOnly yes` overrides whatever the
agent has loaded.

Smoke-test:

```bash
# === LAPTOP ===
ssh bastion exit       # should connect, then return immediately
ssh controller exit    # transparent ProxyJump via bastion
ssh compute-1 exit
ssh compute-2 exit
```

If any of those fail, **stop here** — the rest of the flow assumes laptop SSH
works. Most common cause: wrong `ssh_private_key_path` in `terraform.tfvars`.
Fix and re-paste the snippet.

## Step 2 — (Auto) Kolla inventory + `globals.yml` NIC names

Two files are auto-managed for you:

**`kolla-config/multinode`** — re-rendered from
`azure/terraform/multinode.tftpl` on every `terraform apply` using
`controller_ip` / `compute_ips` / `admin_username` from your variables.
The header of the rendered file says "GENERATED BY TERRAFORM — DO NOT EDIT
BY HAND" — make changes in the template, then re-apply. No manual sync
between Terraform IPs and Kolla inventory.

**`kolla-config/globals.yml` NIC names** — Azure VMs use `eth0`/`eth1`;
the shared file ships with AWS's `ens5`/`ens6`.
`scripts/01-setup-bastion.sh` (Step 8) detects the Azure cloud marker
written by cloud-init and rewrites the NIC names automatically.

Just verify both are in known states before continuing:

```bash
# === LAPTOP ===
# multinode: should show your Terraform IPs (10.0.2.10 / 10.0.2.21 / 10.0.2.22).
head -50 /Users/hanzo/code/openstack/prod-setup/kolla-config/multinode

# globals.yml: ens5/ens6 (will be rewritten) OR eth0/eth1 (already Azure-correct).
grep -E '^(network_interface|neutron_external_interface):' \
  /Users/hanzo/code/openstack/prod-setup/kolla-config/globals.yml
```

If `globals.yml` shows anything other than `ens5/ens6` or `eth0/eth1`,
restore the file from git (`git checkout
prod-setup/kolla-config/globals.yml`) so Step 8 has a known starting point.

If `kolla-config/multinode` doesn't have your IPs, you skipped a `terraform
apply` after a variable change — re-run `terraform apply` (no infra
changes will be made; only the file is re-rendered).

## Step 4 — Copy your laptop key to the bastion

This is the linchpin. We give the bastion an explicit copy of the key that's
already authorized on every node, so it can bootstrap its own SSH trust without
depending on agent forwarding.

```bash
# === LAPTOP ===
scp ~/.ssh/openstack-prod bastion:~/.ssh/laptop_key
ssh bastion 'chmod 600 ~/.ssh/laptop_key'

# Sanity check — fingerprint should match the key in your terraform.tfvars
ssh bastion 'ssh-keygen -l -f ~/.ssh/laptop_key'
```

## Step 5 — Install the bastion's SSH key on every node

The bastion needs passwordless SSH to all three private nodes so Kolla-Ansible
can drive them.

```bash
# === BASTION ===  (after `ssh bastion`)

# Generate the bastion's keypair (skip if already present)
[ -f ~/.ssh/id_rsa ] || ssh-keygen -t rsa -b 4096 -N "" -f ~/.ssh/id_rsa

PUB=$(cat ~/.ssh/id_rsa.pub)

for HOST in 10.0.2.10 10.0.2.21 10.0.2.22; do
  ssh -i ~/.ssh/laptop_key \
      -o IdentitiesOnly=yes \
      -o IdentityAgent=none \
      -o IdentityFile=/dev/null \
      -o StrictHostKeyChecking=accept-new \
      ubuntu@$HOST \
    "grep -qF '$PUB' ~/.ssh/authorized_keys 2>/dev/null || \
     (mkdir -p ~/.ssh && chmod 700 ~/.ssh && \
      echo '$PUB' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys)"
done
```

What each flag does (and why each is mandatory):

| Flag                         | Purpose                                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------- |
| `-i ~/.ssh/laptop_key`       | Use the laptop key Terraform installed via `admin_ssh_key` — known authorized.      |
| `-o IdentitiesOnly=yes`      | Offer **only** the `-i` key, not also try the agent.                                |
| `-o IdentityAgent=none`      | Ignore the forwarded laptop agent entirely. (macOS keychain leaks 6+ keys into it.) |
| `-o IdentityFile=/dev/null`  | Block auto-discovery of `~/.ssh/id_*` files on the bastion.                         |
| `-o StrictHostKeyChecking=…` | Auto-accept the node's host key on first contact (no interactive prompt).           |

Result: exactly **one** auth attempt per host with a known-good key. This is the
single most reliable form — don't substitute `ssh-copy-id`.

Verify. **Important**: if you SSH'd into the bastion with agent forwarding
(macOS default), plain `ssh` here will offer all 6+ keys from your laptop's
keychain via the forwarded agent and trip `MaxAuthTries=6` before reaching the
bastion's own `id_rsa`. Cut the forwarded agent for this shell first:

```bash
# === BASTION ===
unset SSH_AUTH_SOCK    # ignore the forwarded laptop agent for this session

ssh ubuntu@10.0.2.10 hostname    # → openstack-prod-controller
ssh ubuntu@10.0.2.21 hostname    # → openstack-prod-compute-1
ssh ubuntu@10.0.2.22 hostname    # → openstack-prod-compute-2
```

Keep `SSH_AUTH_SOCK` unset for the rest of the deploy — Steps 6–9 all run plain
`ssh`/Ansible against these nodes and need the bastion's own `~/.ssh/id_rsa`,
not the forwarded laptop agent.

If you'd rather not unset it globally, add `-o IdentityAgent=none` to each `ssh`
invocation instead — but Ansible in Step 9 won't pick that up, so `unset` is
simpler.

## Step 6 — Confirm cloud-init finished on every node

> **Now automatic.** `scripts/02-deploy-openstack.sh` opens with a
> "Pre-flight: reachability + cloud-init on all nodes" block that SSH-pings
> every node from the inventory and runs `sudo cloud-init status --wait`
> with retry. If a node is still finalising boot, the script blocks until
> it's ready instead of failing 30 minutes deep. The manual loop below is
> retained only for ad-hoc troubleshooting.

```bash
# === BASTION ===  (only needed if you want to inspect by hand)
for HOST in 10.0.2.10 10.0.2.21 10.0.2.22; do
  echo "=== $HOST ==="
  ssh ubuntu@$HOST 'sudo cloud-init status --wait && \
    test -f /var/log/openstack-prod/00-node-userdata.log && \
    cat /var/log/openstack-prod/00-node-userdata.log'
done
```

Expect `status: done` and the marker file. First boot can take 2–4 minutes;
`--wait` blocks until it's done so this is safe to run early.

## Step 7 — Verify the Cinder data disk on compute nodes

The compute SKUs in this template (`Standard_D2as_v7` / `Standard_D2als_v7`)
have no local resource disk, so the **only** attached data disk is the 40 GB
Cinder volume. The kernel name it gets depends on the disk controller Azure
exposes for that VM size and image:

| Controller        | OS disk   | Data disk | Common on                    |
| ----------------- | --------- | --------- | ---------------------------- |
| **NVMe**          | `nvme0n1` | `nvme0n2` | v6/v7 D-series, most v5 NVMe |
| **SCSI / virtio** | `sda`     | `sdb`     | older D/E-series, B-series   |

Don't assume — inspect first.

### 7a. List the disks on each compute node

```bash
# === BASTION ===
for HOST in 10.0.2.21 10.0.2.22; do
  echo "=== $HOST ==="
  ssh ubuntu@$HOST 'lsblk -dno NAME,SIZE,TYPE | grep -v loop'
done
```

You should see exactly two `disk` entries: one ~80 GB (OS) and one ~40 GB
(Cinder). If the 40 GB disk is missing, the data disk failed to attach — fix
that in Terraform before continuing.

### 7b. Identify the data-disk device path

Pick whichever row in the table below matches your `lsblk` output. Note the
**full device path** — you'll need it in 7d.

| `lsblk` shows…        | Data-disk device       |
| --------------------- | ---------------------- |
| `nvme0n1` + `nvme0n2` | `/dev/nvme0n2`         |
| `sda` + `sdb`         | `/dev/sdb`             |
| anything else         | see "Edge cases" below |

### 7c. Confirm the data disk is unformatted

Substitute the device you identified above for `<DATA_DEV>`:

```bash
# === BASTION ===
DATA_DEV=/dev/nvme0n2     # or /dev/sdb — set to match Step 7b

for HOST in 10.0.2.21 10.0.2.22; do
  ssh ubuntu@$HOST "sudo blkid $DATA_DEV || echo 'unformatted (good)'"
done
```

Every host should print `unformatted (good)`. If `blkid` reports an existing
filesystem or LVM signature, the disk was reused — wipe it
(`sudo wipefs -a $DATA_DEV` on the affected host) before Step 9.

### 7d. Make sure the deploy script can find the device

`scripts/02-deploy-openstack.sh` does **auto-detection** — it tries a list of
well-known device paths in order and uses the first one that exists as a block
device. List the candidates it currently knows about:

```bash
# === BASTION ===
grep -nE '/dev/(sd|nvme|xvd|vd)' ~/openstack/prod-setup/scripts/02-deploy-openstack.sh
```

You should see entries like `/dev/nvme1n1` (AWS Nitro), `/dev/nvme0n2` (Azure
v6/v7 NVMe), `/dev/sdb` (older SCSI/virtio), `/dev/xvdb` (Xen).

**If the device from 7b is in that list**, no change needed — proceed to Step 8.

**If it isn't** (e.g. a new SKU exposes the disk under a different path), don't
sed-rewrite an existing entry — that breaks other platforms. Use one of these
instead:

- **Quick override (recommended)**: export `CINDER_DISK` for this run. The
  script honours it and skips auto-detection:

  ```bash
  # === BASTION ===
  export CINDER_DISK=/dev/<your-device>   # from Step 7b
  ```

- **Permanent**: add a new branch to the auto-detect chain in
  `scripts/02-deploy-openstack.sh` (Step 1, around the `if [[ -b /dev/... ]]` chain near the top) so future deploys on
  the same platform Just Work, and send a PR.

Re-run the `grep` if you patched the script and confirm your device is in the
list.

### Edge cases

- **More than one extra data disk** (e.g. someone added a second Terraform
  `azurerm_managed_disk`): the 40 GB one is Cinder; ignore the others or remove
  them before deploy.
- **Disk already mounted** (`MOUNTPOINT` non-empty in `lsblk`): cloud-init or a
  prior run claimed it. Unmount and wipe before re-deploying.
- **Mixed device names across hosts** (e.g. compute-1 is NVMe but compute-2 is
  SCSI): unusual but possible if the SKUs differ. The Kolla approach in this
  repo expects one device path for all compute nodes — make the SKUs match in
  Terraform, or override per-host in `kolla-config/multinode` and a custom
  inventory variable.

## Step 8 — Run the bastion setup script

```bash
# === BASTION ===
cd ~/openstack/prod-setup
bash scripts/01-setup-bastion.sh
```

The script's first action is `sudo cloud-init status --wait`, so it's safe
to run the moment SSH lets you in — no manual "give the bastion a few
minutes" wait. If cloud-init is still booting, the script blocks until
it's done; if cloud-init reported a failure, it aborts with a pointer to
`/var/log/cloud-init-output.log`.

After that it installs Kolla-Ansible into a Python venv, copies configs to
`/etc/kolla/`, and generates random passwords for all OpenStack services.

The script detects the cloud provider via `/etc/openstack-prod/cloud` (written
by `bastion-userdata.sh` on first boot) and applies cloud-specific patches
automatically:

- **On Azure**: rewrites `network_interface` / `neutron_external_interface` in
  `kolla-config/globals.yml` from `ens5`/`ens6` to `eth0`/`eth1` (so Step 2's
  manual sed is no longer needed).
- **On both AWS and Azure**: applies the VIP-pingability precheck patch.
  Both clouds pre-assign the VIP `10.0.2.250` as a secondary IP on the
  controller's NIC (AWS: `aws_network_interface.controller_mgmt`; Azure:
  the second `ip_configuration` block on
  `azurerm_network_interface.controller_mgmt`). That makes the VIP answer
  pings before keepalived has claimed it, which Kolla's
  `loadbalancer : Checking if kolla_internal_vip_address … are not pingable
  from any node` precheck rejects with rc=0 from `ping`. The patch flips
  `failed_when` on that task to `false` so the precheck passes. (Earlier
  versions of this doc claimed Azure didn't pre-route the VIP — that was
  wrong; the precheck fires on Azure too.)

It also probes SSH to all three nodes up front; if Step 5 worked, the script
skips the interactive key-copy prompt and runs through to completion. If a
probe fails, redo Step 5.

## Step 9 — Deploy OpenStack (in tmux)

This takes **45–60 minutes**. Run inside `tmux` so a flaky SSH session doesn't
kill the deploy mid-run:

```bash
# === BASTION ===
tmux new -s deploy
cd ~/openstack/prod-setup
bash scripts/02-deploy-openstack.sh

# Detach (deploy keeps running):  Ctrl-b then d
# Reattach later:                  tmux attach -t deploy
```

Deploy phases:

| Phase             | Duration | What it does                                         |
| ----------------- | -------- | ---------------------------------------------------- |
| bootstrap-servers | ~5 min   | Configures Docker, kernel params, NTP on all nodes   |
| prechecks         | ~3 min   | Validates ports, disks, Docker, network interfaces   |
| deploy            | ~35 min  | Pulls Docker images, starts all OpenStack containers |
| post-deploy       | ~2 min   | Generates admin credentials (`admin-openrc.sh`)      |

Kolla is idempotent — if a step fails, fix the issue and re-run from the top.

> **Watch for**: during the **deploy** phase, the task
> `mariadb : Wait for MariaDB service to be ready through VIP` is the most
> common point of first-time failure on small controllers. There are two
> distinct flavours of this failure (see the helper docstring in
> `scripts/02-deploy-openstack.sh` near `sync_monitor_passwords`):
>
> - **Timing race** — ProxySQL probed MariaDB before it had finished
>   first-boot init, marked the backend `SHUNNED`, and won't re-probe on
>   its own. A simple `docker restart proxysql` clears it.
> - **Auth drift** — MariaDB's `monitor` user and ProxySQL's stored
>   `mysql-monitor_password` (in the persistent `proxysql.db` SQLite file)
>   drifted apart. Restarting ProxySQL alone does NOT fix this; ProxySQL
>   re-loads the same stale password and keeps failing auth. Symptom:
>   `Access denied for user 'monitor'@'<vip>'` repeating every ~8s in
>   `/var/log/kolla/proxysql/proxysql.log`.
>
> The script handles BOTH automatically in two layers:
>
> 1. **Pre-deploy sync** — runs before every `kolla-ansible deploy`. If
>    the `mariadb` and/or `proxysql` containers are running, the script
>    sets the `monitor` user's password on MariaDB **and** updates
>    ProxySQL's `mysql-monitor_password` global variable from
>    `/etc/kolla/passwords.yml` (then `LOAD … TO RUNTIME; SAVE … TO DISK`
>    so the new value survives a restart). You'll see
>    `Pre-deploy: ensuring monitor passwords are in sync (MariaDB + ProxySQL)`
>    in the log. Idempotent and a no-op on a clean first deploy.
> 2. **Reactive recovery** — if the deploy still fails with
>    `Max connect timeout reached while reaching hostgroup 0`, the script
>    re-runs the dual-side sync, restarts proxysql, queries the backend
>    status (`SELECT … FROM runtime_mysql_servers` — should now be
>    `ONLINE`), and retries the deploy **once**. Look for
>    `Detected ProxySQL backend SHUNNED race` in the log when it kicks in.
>
> If the auto-retry *also* fails, see the **Recovery recipe: ProxySQL
> backend stuck SHUNNED** section below for the deeper wipe-and-redeploy
> fix. Opt out with
> `OPENSTACK_DISABLE_PROXYSQL_AUTORECOVERY=1 bash scripts/02-deploy-openstack.sh`.

## Step 10 — Verify the cluster is healthy

```bash
# === BASTION ===
bash scripts/03-verify.sh
```

Or check by hand:

```bash
# === BASTION ===
source /etc/kolla/admin-openrc.sh
openstack --insecure service list           # all services should be "up"
openstack --insecure hypervisor list        # 2 hypervisors
openstack --insecure network agent list     # all alive=:-)
```

> **Why this works from the bastion**: the `internal-nsg` (see
> `azure/terraform/main.tf` Section 5) explicitly allows TCP from the
> public subnet (`10.0.1.0/24` — bastion only) to all destination ports,
> plus ICMP. Without that rule the OpenStack API calls above would hang
> because Keystone (5000), Glance (9292), Nova (8774), … all live on the
> VIP `10.0.2.250` inside the private subnet.

## Step 11 — Access the Horizon dashboard

```bash
# === LAPTOP ===  (open SSH tunnel — leave this terminal open)
ssh -L 8080:10.0.2.250:80 bastion

# Then in a browser, open:
#   http://localhost:8080
```

The `ssh -L` forward terminates on the bastion, which then opens a TCP
connection to `10.0.2.250:80` (Horizon behind HAProxy). The same
`AllowOpenStackAPIsFromBastionSubnet` NSG rule from Step 10 is what makes
this connection succeed; if you ever lock the NSG down further, remember
to keep ports 80 (Horizon) and 6080 (noVNC console) open from the bastion.

Get the admin password:

```bash
# === BASTION ===  (in a different terminal, or before opening the tunnel)
grep keystone_admin_password /etc/kolla/passwords.yml
```

Login: username `admin`, password from above. You're in.

## Step 12 — Cleanup the bootstrap key

The `laptop_key` on the bastion is no longer needed once Kolla finished
deploying — Ansible uses the bastion's own `id_rsa` from now on.

```bash
# === BASTION ===
shred -u ~/.ssh/laptop_key
```

## Common failure points and fixes

| Symptom                                                                                                                                              | Root cause                                                                                                                                                                                    | Fix                                                                                                                            |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `Too many authentication failures` in Step 5 loop                                                                                                    | You skipped one of the three bypass flags                                                                                                                                                     | Use **all** of `IdentitiesOnly=yes`, `IdentityAgent=none`, `IdentityFile=/dev/null` together                                   |
| `Too many authentication failures` on plain `ssh`                                                                                                    | Forwarded laptop agent leaks keys into bastion sshd                                                                                                                                           | `unset SSH_AUTH_SOCK` on the bastion (or add `-o IdentityAgent=none` to the ssh call)                                          |
| `Permission denied (publickey)` in Step 5                                                                                                            | `~/.ssh/laptop_key` is wrong key or wrong perms                                                                                                                                               | Re-run Step 4; verify fingerprint matches `ssh_public_key` from terraform.tfvars                                               |
| `prechecks` says "interface ens5 not found"                                                                                                          | Skipped Step 2                                                                                                                                                                                | Edit `globals.yml` (laptop), redo Step 3 to sync to bastion, re-run Step 9                                                     |
| `prechecks` says "VG cinder-volumes not found"                                                                                                       | Cinder disk at unexpected path (NVMe vs SCSI, etc.)                                                                                                                                           | Redo Step 7: identify the actual data-disk device with `lsblk`, then patch `scripts/02-deploy-openstack.sh` to match (Step 7d) |
| `MariaDB: Address already in use` on controller                                                                                                      | VIP and management IP collision                                                                                                                                                               | Already pre-empted by `api_interface_address: "10.0.2.10"` in globals.yml — verify it's still set                              |
| `Wait for MariaDB service to be ready through VIP` retries 6× then fails with `Max connect timeout reached while reaching hostgroup 0 after 12005ms` | ProxySQL probed MariaDB before it was ready, marked the backend `SHUNNED`/`OFFLINE`, never re-probed (containers report "healthy" because that only checks ProxySQL itself, not its backends) | See **Recovery recipe: ProxySQL backend stuck SHUNNED** below                                                                  |
| Same `Wait for MariaDB through VIP` failure, AND `/var/log/kolla/proxysql/proxysql.log` repeats `[ERROR] ProxySQL Error: Access denied for user 'monitor'@'<vip>' (using password: YES)` every ~8 seconds | Auth drift: MariaDB's `monitor` user and ProxySQL's stored `mysql-monitor_password` (in the persistent `proxysql.db`) have diverged. Restart alone won't fix this — ProxySQL re-loads the same stale password | Auto-recovery (latest `02-deploy-openstack.sh`) handles this — re-pull the script and run; otherwise see **Fix B** in the recovery recipe below to update both sides by hand |
| `02-deploy-openstack.sh` exits with `ERROR: /etc/kolla/passwords.yml is not readable as user 'ubuntu'` | A partial earlier run (or a manual `sudo` invocation) left `/etc/kolla` owned by root | `sudo chown -R ubuntu:ubuntu /etc/kolla` then re-run                                                                            |
| `02-deploy-openstack.sh` exits with `ERROR: failed to parse controller / compute IPs from $INVENTORY` | `~/multinode` is malformed or its `[control]`/`[compute]` host-group sections are empty | Re-run `bash scripts/01-setup-bastion.sh` (it copies a fresh inventory from `kolla-config/multinode`, which Terraform regenerates) |
| Step 1 LVM aborts on a compute node with `CINDER_DISK=… is currently in use by the OS. Refusing.` | The disk path you exported is the OS root disk (or a partition of it) | `lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS` on the compute, pick the unmounted ~40 GB disk, set `CINDER_DISK=/dev/<that>` and re-run    |
| Step 1 LVM logs `$DISK has stale signatures — wipefs -a to clear them...` | The data disk has leftover FS / partition / LVM headers from an earlier deploy or a snapshot | Informational — the script clears them automatically. No action needed unless you actually wanted that data preserved (you don't on a Cinder VG) |
| `bootstrap-servers`, `prechecks`, or `post-deploy` succeed only on the second attempt (after a `WARN: … failed; sleeping … then retrying once...` line) | Transient apt 502, DNS blip, Docker registry rate-limit, or HAProxy backend flap right after Step 4 | Informational — the script retries each phase exactly once, automatically |
| `terraform output ssh_config` shows wrong key path                                                                                                   | `ssh_private_key_path` var not set                                                                                                                                                            | Set `ssh_private_key_path = "~/.ssh/your-key"` in `terraform.tfvars`, re-apply (no infra change), re-paste                     |
| Deploy stalls on a Docker pull                                                                                                                       | Transient registry timeout                                                                                                                                                                    | Re-run `02-deploy-openstack.sh` — Kolla resumes from where it stopped                                                          |
| `openstack service list` from the bastion hangs / times out, or `ssh -L 8080:VIP:80` shows "connection refused"                                      | NSG was edited to drop the `AllowOpenStackAPIsFromBastionSubnet` rule (or you're on an older version of `main.tf` from before that rule existed)                                              | `terraform apply` after pulling the latest `main.tf` — restores TCP-from-bastion-subnet on all ports                           |
| `terraform plan` says "Missing required provider hashicorp/local"                                                                                    | The Kolla-inventory templating added a new provider; your `.terraform/` is from before that                                                                                                   | `terraform init -upgrade` once, then `terraform plan` again                                                                    |
| Bastion VM "must be replaced" in `terraform plan` after editing `bastion-userdata.sh`                                                                | The VM resources have `lifecycle { ignore_changes = [..., custom_data] }` to prevent this. If you removed it, any byte change to userdata forces destruction (loses `~/.ssh/laptop_key` etc.) | Restore the `ignore_changes`, or `terraform taint` the VM intentionally if you really do want to re-bootstrap from new userdata |
| `loadbalancer : Checking if kolla_internal_vip_address … are not pingable from any node` fails on the controller with `3 packets transmitted, 3 received, 0% packet loss` | You're running an older `01-setup-bastion.sh` that skipped the VIP-precheck patch on Azure. The Terraform-assigned VIP secondary IP makes the controller answer pings on `.250` before keepalived claims it, which the upstream precheck rejects | Re-pull the latest scripts, then `bash scripts/01-setup-bastion.sh` on the bastion (it idempotently applies the patch with the marker `VIP pre-assigned by Terraform`), then `bash scripts/02-deploy-openstack.sh` to resume |

## Recovery recipes

Multi-step fixes for failure modes that don't reduce to a single command. Run
from the bastion unless noted.

### Recovery recipe: ProxySQL backend stuck SHUNNED

> **Auto-recovery built in.** `scripts/02-deploy-openstack.sh` handles
> both flavours of this failure (timing race + auth drift) automatically:
>
> 1. **Pre-deploy sync** — before each `kolla-ansible deploy` run, the
>    script checks whether the `mariadb` and/or `proxysql` containers are
>    running. For each one that's up, it sets/updates the monitor
>    password from `/etc/kolla/passwords.yml`:
>    - MariaDB: `ALTER USER 'monitor'@'%' …`
>    - ProxySQL admin: `UPDATE global_variables SET variable_value=…
>      WHERE variable_name='mysql-monitor_password'; LOAD … TO RUNTIME;
>      SAVE … TO DISK;`
>
>    Idempotent — no-op on a clean first deploy where neither container
>    exists yet; fixes the auth-drift case on re-runs after a partial
>    earlier failure.
>
> 2. **Reactive recovery** — if the deploy still fails on
>    `Wait for MariaDB service to be ready through VIP` with
>    `Max connect timeout reached while reaching hostgroup 0`, the script
>    re-runs the dual-side sync, restarts proxysql, queries
>    `runtime_mysql_servers` to confirm `status = ONLINE`, and retries
>    the deploy **once**.
>
> You should only need this manual recipe if you've opted out
> (`OPENSTACK_DISABLE_PROXYSQL_AUTORECOVERY=1`) or if the auto-recovery's
> `runtime_mysql_servers` query still shows non-`ONLINE` after restart
> (meaning the persistent `proxysql.db` is corrupt enough that we need to
> wipe it).

**Symptom**: Step 9 fails on
`mariadb : Wait for MariaDB service to be ready through VIP` after 6 retries,
with `Max connect timeout reached while reaching hostgroup 0 after 12005ms`.

**Why this happens — two flavours**:

- **Timing race**: On a fresh deploy, ProxySQL starts and runs its internal
  monitor against the MariaDB backend within seconds. If MariaDB is still
  doing first-boot initialization (creating system tables, running
  `mariadb-install-db`), the monitor fails, ProxySQL marks the backend
  `SHUNNED` or `OFFLINE_HARD`, and **does not retry on its own** once
  MariaDB later becomes healthy. The container health check only verifies
  ProxySQL is alive — not that any backend is reachable through it. Result:
  every container reports "healthy", the VIP works, direct
  `mariadb -h <controller> -P 3306` works, but the Ansible task that goes
  _through ProxySQL_ keeps timing out.
- **Auth drift**: A previous partial deploy or password regeneration left
  MariaDB's `monitor` user and ProxySQL's stored
  `mysql-monitor_password` (in the persistent `proxysql.db` SQLite file)
  with different values. ProxySQL keeps offering the stale password and
  MariaDB keeps rejecting it. Distinctive log signature in
  `/var/log/kolla/proxysql/proxysql.log` (every ~8s):
  `[ERROR] ProxySQL Error: Access denied for user 'monitor'@'<vip>'
  (using password: YES)`. Pure restarts won't fix this — the password
  needs to be updated on BOTH sides.

**Diagnostic** — confirm before applying the fix. NB: the `proxysql`
container ships no `mysql`/`mariadb` client, so query its admin port
through the `mariadb` container instead (both are on the host network):

```bash
# === BASTION ===
CTRL=10.0.2.10
PSQL_PW=$(ssh ubuntu@$CTRL "sudo grep '^proxysql_admin_password:' /etc/kolla/passwords.yml | awk '{print \$2}'")

ssh ubuntu@$CTRL "sudo docker exec mariadb mariadb -uadmin -p'$PSQL_PW' \
  -h127.0.0.1 -P6032 \
  -e 'SELECT hostgroup_id, hostname, port, status FROM runtime_mysql_servers'"

# And check the auth-drift signature:
ssh ubuntu@$CTRL "sudo docker exec proxysql tail -20 /var/log/kolla/proxysql/proxysql.log"
```

If `status` is `SHUNNED`, `OFFLINE_SOFT`, or `OFFLINE_HARD`, you've hit
this. If the log shows `Access denied for user 'monitor'`, you're on the
auth-drift flavour and need both-side sync (Fix B), not just a restart.

**Fix A — timing race only (no auth-denied lines)**: kick ProxySQL so it
re-probes against the now-healthy MariaDB:

```bash
# === BASTION ===
ssh ubuntu@$CTRL "sudo docker restart proxysql"
sleep 15

ssh ubuntu@$CTRL "sudo docker exec mariadb mariadb -uadmin -p'$PSQL_PW' \
  -h127.0.0.1 -P6032 \
  -e 'SELECT hostgroup_id, hostname, port, status FROM runtime_mysql_servers'"
# expect: status = ONLINE
```

Then re-run the deploy:

```bash
# === BASTION ===
cd ~/openstack/prod-setup
bash scripts/02-deploy-openstack.sh
```

**Fix B — auth drift (log shows `Access denied for user 'monitor'`)**:
update the password on BOTH sides from `passwords.yml`, persist on the
ProxySQL side, then restart and verify:

```bash
# === BASTION ===
ROOT_PW=$(ssh ubuntu@$CTRL "sudo grep '^database_password:' /etc/kolla/passwords.yml | awk '{print \$2}'")
MON_PW=$( ssh ubuntu@$CTRL "sudo grep '^mariadb_monitor_password:' /etc/kolla/passwords.yml | awk '{print \$2}'")

# MariaDB side: ALTER USER over the unix socket
ssh ubuntu@$CTRL "sudo docker exec -i mariadb mariadb -uroot -p'$ROOT_PW' \
  -S /var/lib/mysql/mysql.sock" <<SQL
CREATE USER IF NOT EXISTS 'monitor'@'%' IDENTIFIED VIA mysql_native_password USING PASSWORD('$MON_PW');
ALTER  USER             'monitor'@'%' IDENTIFIED VIA mysql_native_password USING PASSWORD('$MON_PW');
GRANT USAGE, REPLICATION CLIENT, PROCESS ON *.* TO 'monitor'@'%';
FLUSH PRIVILEGES;
SQL

# ProxySQL side: UPDATE admin var + LOAD/SAVE so it survives a restart
ssh ubuntu@$CTRL "sudo docker exec mariadb mariadb -uadmin -p'$PSQL_PW' \
  -h127.0.0.1 -P6032 \
  -e \"UPDATE global_variables SET variable_value='$MON_PW' \
        WHERE variable_name='mysql-monitor_password'; \
       LOAD MYSQL VARIABLES TO RUNTIME; \
       SAVE MYSQL VARIABLES TO DISK;\""

# Bounce proxysql, then verify ONLINE
ssh ubuntu@$CTRL "sudo docker restart proxysql"
sleep 20
ssh ubuntu@$CTRL "sudo docker exec mariadb mariadb -uadmin -p'$PSQL_PW' \
  -h127.0.0.1 -P6032 \
  -e 'SELECT hostgroup_id, hostname, port, status FROM runtime_mysql_servers;'"

# Resume the deploy
cd ~/openstack/prod-setup
bash scripts/02-deploy-openstack.sh
```

**Fix C — nuclear (still stuck after A or B)**: the persistent
`proxysql.db` is corrupt enough that the surgical updates don't take.
Wipe ProxySQL's volume and let Kolla rebuild it. Safe — MariaDB data is
on a *separate* volume that we leave alone:

```bash
# === BASTION ===
ssh ubuntu@$CTRL "sudo docker rm -f proxysql && sudo docker volume rm proxysql"

source ~/kolla-venv/bin/activate
kolla-ansible deploy -t loadbalancer -i ~/multinode   # rebuilds proxysql/haproxy/keepalived
cd ~/openstack/prod-setup
bash scripts/02-deploy-openstack.sh                   # resumes the full deploy
```

If even Fix C doesn't recover it, the MariaDB Galera state itself may be
wedged. Run the upstream cluster recovery playbook, then redeploy:

```bash
# === BASTION ===
source ~/kolla-venv/bin/activate
kolla-ansible -i ~/multinode mariadb_recovery
cd ~/openstack/prod-setup
bash scripts/02-deploy-openstack.sh
```

**Why we don't preempt this in the deploy script**: the race is timing dependent
and only triggers on cold first-boots of MariaDB on small controllers. Detecting
and force-restarting ProxySQL on every deploy would mask real backend failures
during legitimate re-runs.
